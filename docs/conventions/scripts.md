# 脚本规范 · 测试/调试脚本的存放与注释

> 适用范围:本仓全部一次性、调试、验证类脚本。规约地图见根目录 `AGENTS.md`。

## 1. 问题背景

临时脚本随手丢在模块根目录(如 `src/server/_q_nodes.py`),会带来:

- 目录污染:根目录本应只有配置与入口,混入脚本后职责不清
- 来路不明:没人知道它测什么、怎么跑、能不能删
- 无法维护:与正式单测/运维脚本混在一起,无法区分生命周期

## 2. 脚本分类与归属目录

| 类型 | 归属目录 | 生命周期 | 示例 |
| --- | --- | --- | --- |
| 自动化单测 | `<module>/tests/` | 长期,随验证基线跑 | `test_node_sync.py` |
| 运维/迁移/一次性操作 | `<module>/scripts/` | 长期或一次性 | `migrate_sqlite_to_pg.py` |
| 临时调试/验证脚本 | `<module>/scripts/` | 验证完可保留(见 §3) | `query_nodes.py` |
| 检索评测 | `<module>/eval/` | 长期 | `run_eval.py` |

`<module>` 指 `src/server`、`src/node` 等。前端脚本同理,放各自模块的 `scripts/`。

**铁律:模块根目录禁止出现散装 `.py` 脚本。** `src/server/`、`src/node/` 根下只允许放 `pyproject.toml`、`.env*`、`.python-version`、`MCP_USAGE.md` 等配置与入口文件,脚本一律进 `tests/` 或 `scripts/`。

## 3. 保留与清理

- 验证完成的一次性脚本:**默认删除**;确有必要保留的,必须按 §4 写清头注释后再保留
- 允许保留的典型情形:复现某个 bug、回归对照、日常高频排查工具
- 判断标准:别人只看文件本身,能否知道"它测什么、怎么跑、何时写的"
- 禁止保留:一次性、无注释、且已确认无复用价值的脚本

## 4. 头注释模板(保留脚本必须)

```python
"""<一句话说明脚本做什么>。

测试/验证内容:
- <被测对象或链路 1>
- <被测对象或链路 2>

前置条件:
- <需要的服务/数据库/环境变量>

运行方式:
- cd src/server && uv run python scripts/xxx.py
"""
```

- 注释语言与正文一致(中文)
- "测试/验证内容"必须写具体对象(表名、端点、链路),不写"测试功能"这类空话
- 脚本从 `.env` / `app.config` 读取配置,**禁止硬编码密钥、连接串**

## 5. 命名

- 动词开头表明动作:`query_`、`backfill_`、`check_`、`dump_`、`migrate_`
- 禁止 `_q_`、`tmp`、`test1`、`aaa` 这类无意义前缀/名字
- 下划线前缀(`_xxx.py`)**不再表示"临时"**;文件名须与头注释描述一致

## 6. 红线自查

- [ ] 模块根目录无散装脚本
- [ ] 保留的脚本均有头注释,写清测什么、怎么跑
- [ ] 脚本未硬编码密钥/连接串(从 `.env` 或 config 读)
- [ ] 脚本归属目录正确(tests / scripts / eval)
