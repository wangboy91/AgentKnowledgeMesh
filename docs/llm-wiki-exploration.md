# LLM wiki + RAG 协同 · 设计探索

> 状态:**探索阶段,未立项**。本文是想法推演记录,不是已采纳的架构决策。
> 结论收敛后应转为 openspec 变更提案;若方向被否决,本文留档说明理由。
> 日期:2026-09-17

## 1. 动机

纯 RAG(分块 + 向量/关键词检索)在三类问题上表现不佳:

| 痛点 | 纯 RAG | + LLM wiki 提炼层 |
| --- | --- | --- |
| 跨文档综合("这几个方案对比结论是什么") | 检回碎片让上层 LLM 现场拼,易漏、浪费 context | wiki 页天然是综合后的结论 |
| token 效率 | 原文块冗余度高 | 提炼页信噪比高,正好喂 LLM |
| 个人/团队知识沉淀 | 每次问答从零开始 | 洞察持续累积、可复用 |
| "印象类"问题("我记得大概……") | 向量对碎片原文不敏感 | 对提炼页语义匹配更准 |

这也是当前领域的收敛方向(DeepWiki、GraphRAG 的社区摘要层、Anthropic memory 工具,本质都是"LLM wiki"思想)。

**前提事实**:AKM 目前没有任何生成式 LLM 依赖,唯一的模型调用是云端 embedding。引入 wiki 提炼层 = AKM 的第一个 LLM 依赖,是架构级决策。

## 2. 核心分叉:wiki 由谁写

```
Model A: 服务端提炼管线                 Model B: Agent 记忆层
+--------------------------+          +--------------------------+
| AKM server 内跑 LLM job  |          | AKM 只提供结构化存储+API  |
| 语料 -> 自动生成 wiki 页 |          | wiki 页由消费方 Agent 写  |
| (AKM 是"编辑")           |          | (Agent 是"作者")         |
+--------------------------+          +--------------------------+
  AKM 承担: LLM 配置/成本/质量           AKM 承担: 存储/溯源/检索/同步
  优点: 所有消费者受益(MCP/REST/Web)      优点: 基础设施定位不动摇
        语料级综合(跨文档)                     无服务端 LLM 成本
  缺点: AKM 变重,引入 LLM 依赖             缺点: 质量取决于各 Agent
        幻觉责任在 AKM                        无语料级综合能力
```

**判断:不是二选一,而是上下两层(Model C)**

```
+--------------------------------------------------+
| 检索编排层: 结果带 kind(derived/raw),消费方自选  |
+--------------------------------------------------+
| 提炼层 A: 服务端 distiller job(可插拔,按需触发) |
|   语料级综合: 概念页/对比页/决策页               |
+--------------------------------------------------+
| 提炼层 B: Agent 写入通道(MCP 工具 / API)        |
|   个体洞察沉淀: "record insight"                |
+--------------------------------------------------+
| 基座: wiki 页 = 一等 Document 子类型             |
|   带溯源元数据,进现有混合检索,走现有同步         |
+--------------------------------------------------+
```

关键洞察:**wiki 页不是新的顶层概念,而是 Document 的子类型**(`doc_type=derived`)加溯源元数据。现有混合检索、文档树、多节点同步、MCP 几乎零改动即覆盖 wiki 页。

## 3. 溯源与新鲜度:hash 字段是现成的钥匙

`Document` 已有 `hash` 字段,新鲜度检测可以完全确定性、零 LLM 成本:

```
wiki 页(derived document)
  derived_from: [
    {doc_id: 42, hash: "a1b2..."},   <- 生成时刻的源文档 hash
    {doc_id: 87, hash: "c3d4..."},
  ]
  generated_at, generator(哪个模型/哪个 agent), status

新鲜度检测(确定性):
  每次扫描/同步后:
    for 每个 derived 文档:
      对比 derived_from[i].hash 与源文档当前 hash
      任一不匹配 --> 标记 stale
```

- stale 检测纯 hash 对比,可挂在现有 scanner/sync 管道里顺手做
- stale 是状态而非事件:检索时 stale 页可降权、带警告返回或不返回,策略可配置
- 重生成按需触发:只有 stale 且再次被查询/引用时才跑,成本可控

**源文档被删除**:倾向 wiki 页保留并标记 `orphaned`(内容仍有效但无法验证),而非级联删除——历史洞察有价值,AKM 不替用户做删除决定。

## 4. 检索编排:不要过度设计路由

阶段一不需要"智能路由":

```
Query --> 混合检索(现有管道, wiki 页已入索引)
              |
              v
         结果列表: [{kind: "derived", ...}, {kind: "raw", ...}]
              |
              v
         消费方(Agent/人) 自己决定怎么用
```

理由:wiki 页本身为 LLM 阅读优化,天然检索友好,让排序自己说话;消费方拿到 `kind` 标记后可自主"先读提炼页、需要原文再跟进 `derived_from`"——这正是 Agent 擅长的多步行为,不需要 server 替它路由。

智能路由(查询意图分类 → 定向检索某一层)留到阶段三,等真实使用数据证明需要再做。

## 5. 个人 vs 企业:同一基座,两种行为

| 维度 | 个人知识库 | 企业知识库 |
| --- | --- | --- |
| wiki 来源 | 主要是 Model B(Agent 洞察沉淀) | 主要是 Model A(语料级综合,团队 wiki) |
| 治理 | 不需要 | 需要:草稿/已审状态?谁能触发 distiller? |
| 冲突处理 | 最新覆盖或并存 | 矛盾不能被"平均掉",必须显式呈现分歧 |
| 成本敏感度 | 高(自己的 API key) | 中(有预算) |

**矛盾处理原则**(须写进 distiller 设计):两份源文档结论相反时,wiki 页应写"存在两种说法,分别源于 X 和 Y",而不是融合出和稀泥的答案。否则 wiki 层会系统性制造错误共识。

## 6. 分布式:提炼在哪跑

```
节点A(电脑1) ---sync---+
节点B(电脑2) ---sync---+--> 中央 server(全局语料视图)
节点C(电脑3) ---sync---+         |
                                v
                    distiller 在 server 跑
                    (只有它看得见合并后的语料)
                                |
                    wiki 页 = 普通文档,随 sync 下发
```

- 提炼只能在 server 跑(语料级综合需要全局视图);产出 wiki 页即普通文档,复用现有同步管道分发
- 节点离线读到 stale wiki 页:可接受,stale 标记会同步过去
- 未来"节点本地提炼"(单机无 server 场景)同一套 Document 子类型照样成立

## 7. 边界自查

- AKM 负责:存储、溯源元数据、stale 检测、检索、同步、LLM 调用管道(可插拔模型配置)
- AKM 不负责:提炼内容的正确性——它是派生物,责任通过 `derived_from` 追溯到源
- 红线:整套机制是纯通用"知识蒸馏",无任何领域词汇,符合产品无关铁律

产品叙事升级:从"分布式文档检索"到"**会越用越聪明的知识库**"——原始层保证可信,提炼层积累智慧,两层都随节点分发。

## 8. MVP 切分

```
切片1(无 LLM): wiki 页 = Document 子类型 + derived_from 元数据
              + hash 对比 stale 标记 + 混合检索返回 kind
切片2(一个 LLM 依赖点): 手动触发的 distiller
              "为这个主题/这组文档生成提炼页"
切片3(写回回路): MCP 工具让 Agent 记录洞察(Model B)
后期:   自动触发(查询阈值)、智能路由、治理状态机、节点本地提炼
```

切片 1 无 LLM 也独立有价值:用户可手工写 wiki 页(它就是带溯源的文档),Agent 可通过现有 API 读到。
