# node-upload-batching · 技术设计

## D1 为什么在节点侧解决，而不是让部署方调 nginx

**选项**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 只调 nginx | 部署文档要求设 `client_max_body_size 100m` | 治标。知识库继续变大仍会撞墙；且要求每个部署方正确设值，漏设即**首次接入静默失败**（只打一行 413 日志，快照不动，无限重试）。失败模式隐蔽且后果严重——用户看到的是"节点连上了但一篇文档都没有" |
| B. 节点分批（本变更） | 单请求体控制在固定上限内，任意规模知识库都能同步 | 治本。把"知识库能有多大"从部署配置中解耦；对端代理保持默认配置也能工作 |
| C. B + 服务端异步接收 | Hub 侧改成任务队列接收 | 过度设计。同步链路本就是幂等的多次调用，分批已足够；引入队列显著增加复杂度与状态管理 |

选 **B**。C 留待确有超大批量需求时再议。A 不作为方案，但**保留为调优手段**写入文档：代理 body 上限 ≥ 批体积时请求数更少、同步更快。

## D2 上限取 `batch_bytes` 还是 `batch_docs`

**两个都要**，因为两个维度的失控方式不同：

- **条数失控**：知识库大量小文件（如上千篇短笔记）。总字节数可能不大，但单请求 JSON 的**数组解析开销**与 Hub 侧单事务的入库规模会偏高。`batch_docs` 限住请求内的条目数。
- **体积失控**：少数超大文档（如单篇几 MB 的技术手册）。条数远未触顶，但字节数已越界。`batch_bytes` 限住请求体体积。

取先到者封批。默认值：`AKM_UPLOAD_BATCH_BYTES=524288`（512 KiB）、`AKM_UPLOAD_BATCH_DOCS=50`。

**为什么默认 512 KiB 而不是贴着 nginx 默认的 1 MiB**：留出余量给 JSON 转义膨胀（中文内容经 `ensure_ascii` 后单字符可膨胀到 6 字节）、HTTP 头与其他字段开销，确保默认配置下的 nginx 一定放行。这不是精确的序列化后体积，而是**保守估算**，宁可多切一批也不冒 413 的风险。

## D3 体积估算口径

不对每篇文档做完整 `json.dumps` 来精确测量（O(n) 重复序列化，浪费 CPU）。采用**估算**：

```
条目体积 ≈ len(content.encode("utf-8")) + len(path) + len(title) + 固定开销常数
```

- `content` 用 UTF-8 字节长度（中文 3 字节/字符），这是主体
- 固定开销常数覆盖 `hash` / `size` 字段与 JSON 键名、引号、逗号（取一个宽裕值）
- 估算**偏保守**（可能高估），因此切出的批次只会更小、不会更大，方向上安全

有意**不**引入 `ensure_ascii` 膨胀折算：请求体由 httpx 以 UTF-8 编码发送（非 ASCII 转义），实际网络字节即 UTF-8 长度，此口径与真实传输一致。估算仍留了常数余量以吸收误差。

## D4 单篇超限为何独占一批而不是报错跳过

若某篇文档本身超过 `batch_bytes`，切分算法若坚持"每批不超限"就会陷入**无法切分**的僵局。处理为**独占一批直接发**：

- 该文档体积再大也只有一个条目，是能做到的最小切分粒度
- 若对端代理上限确实小于该文档，则这一批会 413 失败——**这是诚实的失败**（快照不更新、日志明确），优于静默跳过（用户永远不知道有文档没同步）
- 避免死循环：切分算法必须保证**每轮至少推进一个条目**，否则会无限循环。独占一批是这一保证的兜底

## D5 `deletions` 只随最后一批的两个理由

1. **避免重复删除指令**：Hub 对 `deletions` 的语义是"删除这些路径"，重复发送同一路径在实现上无害（第二次找不到即跳过），但会在响应里产生重复的 `deleted` 计数，令统计失真。只发一次，统计干净。
2. **维持"列表缺失即删除"的关闭状态**：这是 hash-first 协议的关键约定（见 `technical-design.md` §4.2）——`deletions` **键缺失**时 Hub 会按旧版全量语义推导删除，可能误删。因此**每一批**都必须带 `deletions` 键（前序批次为空列表），只有最后一批带真实列表。

## D6 原子性边界：为什么"已成功批次不回滚"

分批引入了"部分成功"这一新状态。两种处理：

- **（选）失败即整体失败，快照不动** —— 语义与既有「SHALL 仅在收到 200 后更新快照」完全一致。下轮重传时，已入库的批次因 `(node_id, path)` + hash 幂等而被 Hub 判为 unchanged（hash-only 或直接忽略），不产生重复数据。代价是少量重复流量，换来语义简单。
- （否）已成功批次写入快照，仅失败批次下轮重试 —— 需要维护"部分快照"状态，且与「快照 = 上次确认同步成功的全量集合」的既有定义冲突（`classify_diff` 以快照为全量基准推导 deletions，部分写入会让未同步的文档在下一轮被误判为删除）。**危险，不采用**。

## D7 局部同步（`sync_paths`）复用同一分批逻辑

`_sync_paths()` 与 `_sync_documents()` 目前各自调 `_upload()`。分批实现放在**批次生成 + 发送这一层**（`batch_payload()` + `_upload_batches()`），两个入口共同调用：

- 局部同步的 payload 天然很小（防抖聚合后的少数文件），通常单批即走完，行为不变
- 但批量导入触发的大批变更事件会经防抖聚合为一次局部同步，此时分批同样生效——不必为局部路径单独写一套

## D8 配置项命名与默认值

沿用现有 `AKM_` 前缀与 `Field(default)` 风格：

```python
upload_batch_bytes: int = Field(512 * 1024)   # AKM_UPLOAD_BATCH_BYTES
upload_batch_docs: int = Field(50)            # AKM_UPLOAD_BATCH_DOCS
```

取值为 `<= 0` 时视为**不限**（该维度不参与切分），便于需要单批全量的场景（如内网直连 Hub、无代理）。两个都为 `<= 0` 即完全退回改动前行为——提供一个明确的逃生舱。
